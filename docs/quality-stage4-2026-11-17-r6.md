## 三、缺陷一：`score_available` 在 5 个消费点被忽略（已修 `ca629bd`）

### 原始现象（走查实测）

注入 `{"score": 50, "level": "数据不足", "score_available": false, "data_quality": {"available_dims": 0}}` 后，工作台顶部标签显示：

```
大盘温度 50.0 · 数据不足
```

**50 恰好落在 40~60 区间**，于是被着色成 `is-warn`。用户读到的是一条"温度中性"的结论，实际是**四维数据全缺**——标着"数据不足"却给数字和颜色，比纯空态更误导。

### 根因

A-08（`10a8817`）在后端加了 `score_available` / `data_quality.available_dims`，也改了温度计表盘与研判文案，但**前端 `thermo` 的 5 个消费点没跟着改**。`workbench.js:151` 只判 `isNum(thermo.score)`。

### 工程师的修复：先立判据，再逐点接入

新增 `thermoUsable(thermo)`：`score_available === false` 或 `data_quality.available_dims === 0` → 不可用。然后**逐个消费点排查（9 处，改 6 处）**：

| # | 消费点 | 结论 |
|---|---|---|
| 1 | `renderHead` → `#wbTempTag` | **改**：不可用时「大盘温度 — · 数据不足」，class 只留 `wb-tag` |
| 2 | `renderHead` → `stale`（live 点） | 不改：已通过 `components.sentiment.note` 含"不可用"判定 |
| 3 | `renderStats` | 不改：只用 `sector_rotation.gain/fall_count`，缺失走 `isNum()` 兜底；「打板温度」取 `board.temperature` 与本缺陷无关 |
| 4 | `renderHold` | 不改：`gain/fall` 为 null 时落到「承接待确认」，不产生结论 |
| 5 | `radarDims` | **改**：旧判据 `!comp.x` 在"对象存在但 available=false"时为 false → 占位 50 被当正常值 |
| 6 | `renderRadar` | **改**：① 缺失维不再画点（旧写法按 50 落在中环，视觉上="这一维中等"）；② 中心综合分改走 `thermoUsable` |
| 7 | `disciplineChecks` | **改**：占位 50 会让「温度 ≥ 50」判成**通过** → 等于用缺失数据伪造一条通过的纪律项；改后回退到 `board.temperature` |
| 8 | `load()` 健康点 `{k:'温度'}` | **改**：修前 `ok = !!thermo` → 四维全缺仍亮绿点；改为 `score_available !== false` |
| 9 | `load()` 的 `update_time` | 不改：只显示抓取时刻，不是结论 |

**其中 5/7/8 比原缺陷更严重**：雷达图把缺失维度画成"中等"，纪律项被伪造成"通过"，健康点亮绿灯。这三处都是**用缺失数据生成结论**，正是本轮红线。

### 验证

修复后走查 B2 变为 `大盘温度 — · 数据不足`；回归 **3081 passed / 1 skipped**（+6 例）。

## 六、真机复核追加发现：涨跌家数**结构性恒为 100/0/0**（P1，最严重）

> 这一步是用**内置浏览器打开线上生产站**做真机复核时发现的，不在原 13 步脚本里。用户建议"可以用内置浏览器当真机"直接促成了这条。

### 现象（线上 2026-11-17 20:00，`GET /api/review/board`）

```
market.rise_count = 100   fall_count = 0   flat_count = 0   rise_ratio = 1.0
market.sentiment_label = 偏多            data_quality = normal
limit.limit_up_count = 37    limit_down_count = 67
temperature = 77.6 偏热，breakdown 里「市场广度 = 100.0」
```

真机界面上同时显示：**「个股涨/平/跌 100/0/0，上涨占比 100.0%」** 与 **「涨停 37 / 跌停 67」**、以及**创业板指 -1.20%**。
100 只全涨、0 只跌，却有 67 家跌停——**界面自己和自己矛盾**。

### 同一时刻的真实值（直连东财核对）

| 市场 | f104(涨) | f105(跌) | f106(平) | 合计 |
|---|---|---|---|---|
| 沪市 `1.000001` | 598 | 1688 | 69 | 2355 |
| 深市 `0.399001` | 638 | 2237 | 64 | 2939 |
| **沪深合计** | **1236** | **3925** | **133** | **5294** |

**真实上涨占比 = 1236 / 5294 = 0.2335** → 按现有阈值（<0.4）应判 **「偏空」**，而线上报的是「偏多」。
（5294 / clist `total` 5564 = 95.1%，差额为北交所与退市标的，量级合理。）

### 根因（`src/core/data_source_v2.py:2470-2515`）

```python
params = {"pn": 1, "pz": 1, "po": 1, "np": 1, "fltt": 2, "invt": 2, "fid": "f3", ...}  # 按涨幅降序
total_count = data["data"]["total"]          # 拿到 5564
params_up["pz"] = min(total_count, 6000)     # 想一次拉全市场
diff = data_up["data"]["diff"]               # ← 实测只返回 100 行
```

**实测复证**：同一个 clist 接口请求 `pz=6000`，**实返 100 行**（`total=5564`）；且 `fid=f3` 降序 ⇒ 这 100 行**全是上涨股** ⇒ `rise=100 / fall=0 / flat=0 / ratio=1.0`。

⇒ **`rise_ratio` 恒等于 1.0**，与当天行情无关，**每天都一样**。三个连带后果：

1. **温度「市场广度」恒 100 分** → 温度系统性偏热（今天 77.6「偏热」里有相当部分是假的）；
2. **`sentiment_label` 恒「偏多」**；
3. **`data_quality` 判 `normal`**（因为 `rise_count > 0`）——把这个错误**包装成"数据正常"**。

### 为什么前五轮都没发现

`git log -S "min(total_count, 6000)"` 显示这段逻辑由 **`053a55c`（2026-06-04）** 引入，**已存活 5 个多月、跨越五轮质量评估**。

前五轮审的是**代码结构**（异常处理、契约、鉴权、并发），没有人问过一句：**"这个 100 是怎么来的？它等于全市场吗？"** 也没有人把 `rise+fall+flat` 与涨停/跌停家数放在一起看。

**这条是本轮方法论的最强证据**：不是"某个字段单位写错了"，而是**样本量被当成了总体**，而且错得极其稳定（每天都返回同一个形状），所以永远不会触发异常、永远 `data_quality=normal`。**只有把两组本该自洽的数字放在一起对照，才能发现。**

### 修复（`59376c1`）

改用东财 `ulist.np` 的聚合字段：沪深各取一次 `f104/f105/f106` 求和；单市重试 1 次，**缺一即 fail-closed**（不拿单市冒充全市场）；`basis`（结论依据）与新增的 `counts_basis`（家数状态）分开表达。

**必须记下的一处口径纠正（我给错了阈值）**：我最初指定的自洽校验是 `家数合计 / clist_total ∈ [0.90, 1.15]`。实测此刻 `clist total = 5930`（不是我先前测到的 5564），因为 `fs` **把北交所也算了进去**，而 ulist 只统计沪深 → `5294/5930 = 89.3%` **低于 0.90，第一版直接被自己的校验打成 partial**。
正确做法：再取一次北交所 `total`（实测 366），**分母 = total − 北交所 = 5564** → 覆盖率 95.1% 才采信；北交所取不到时退回原始 total（宁可 fail-closed，不放宽）。

**同一时刻旧进程 vs 新逻辑对照**（工程师在进程内实测）：

| 指标 | 旧（线上） | 新 |
|---|---|---|
| rise / fall / flat | 100 / 0 / 0 | **1236 / 3925 / 133** |
| `rise_ratio` | 1.0 | **0.2335** |
| `sentiment_label` | 偏多 | **偏空** |
| `counts_available` | True（假） | True（真，覆盖率 95.1%） |
| 温度「市场广度」 | **100.0** | **23.9** |
| 温度总分 | 77.6「偏热」 | **−15.22 分**（权重 0.20）→ 约 62，翻为「偏暖/中性」 |

**连带修的两处**：
1. `market_review.data_quality` 旧判据 `(rise_count or 0) > 0` —— 既靠巧合降级，又会把"全市场下跌 rise=0"误判成 partial；改看 `counts_available` + 非 None。
2. `prediction_service._fetch_sentiment` 不再把 `None` 兜成 `0`，并透传 flags。

**同类"只拿前 N 条当全量"的排查结论**：全仓只剩这一处。`_screen_em_speed` 也用 clist，但它是**显式 Top-N 排序**（语义就是前 N），不构成缺陷。

**遗留（未改，已记录）**：`sentiment.ratio` 含平盘（1236/5294 = 0.2335），而 `_calc_sentiment_score` 不含平盘（1236/5161 = 0.239 → 23.9 分）。同一 payload 里两个"上涨占比"含义不同，当前差 0.5 分不影响结论，但平盘数变大时会发散 → 列入阶段五收口。
