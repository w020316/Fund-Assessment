## 三、唯一的真缺陷：`score_available` 在 5 个消费点被忽略（已修 `ca629bd`）

### 原始现象（走查实测）

注入 `{"score": 50, "level": "数据不足", "score_available": false, "data_quality": {"available_dims": 0}}` 后，工作台顶部标签显示：

```
大盘温度 50.0 · 数据不足
```

**50 恰好落在 40~60 区间**，于是被着色成 `is-warn`。用户读到的是一条"温度中性"的结论，实际是**四维数据全缺**——标着"数据不足"却给数字和颜色，比纯空态更误导。

### 根因

A-08（`10a8817`）在后端加了 `score_available` / `data_quality.available_dims`，也改了温度计表盘与研判文案，但**前端 `thermo` 的 5 个消费点没跟着改**。`workbench.js:151` 只判 `isNum(thermo.score)`。

### 工程师的修复：先立判据，再逐点接入

新增 `thermoUsable(thermo)`：`score_available === false` 或 `data_quality.available_dims === 0` → 不可用。然后**逐个消费点排查（9 处，改 6 处）**：

| # | 消费点 | 结论 |
|---|---|---|
| 1 | `renderHead` → `#wbTempTag` | **改**：不可用时「大盘温度 — · 数据不足」，class 只留 `wb-tag` |
| 2 | `renderHead` → `stale`（live 点） | 不改：已通过 `components.sentiment.note` 含"不可用"判定 |
| 3 | `renderStats` | 不改：只用 `sector_rotation.gain/fall_count`，缺失走 `isNum()` 兜底；「打板温度」取 `board.temperature` 与本缺陷无关 |
| 4 | `renderHold` | 不改：`gain/fall` 为 null 时落到「承接待确认」，不产生结论 |
| 5 | `radarDims` | **改**：旧判据 `!comp.x` 在"对象存在但 available=false"时为 false → 占位 50 被当正常值 |
| 6 | `renderRadar` | **改**：① 缺失维不再画点（旧写法按 50 落在中环，视觉上="这一维中等"）；② 中心综合分改走 `thermoUsable` |
| 7 | `disciplineChecks` | **改**：占位 50 会让「温度 ≥ 50」判成**通过** → 等于用缺失数据伪造一条通过的纪律项；改后回退到 `board.temperature` |
| 8 | `load()` 健康点 `{k:'温度'}` | **改**：修前 `ok = !!thermo` → 四维全缺仍亮绿点；改为 `score_available !== false` |

**其中 5/7/8 比原缺陷更严重**：雷达图把缺失维度画成"中等"，纪律项被伪造成"通过"，健康点亮绿灯。这三处都是**用缺失数据生成结论**，正是本轮红线。
