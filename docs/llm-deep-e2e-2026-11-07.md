### 2.3 对照组：直连上游（**绕过 router**，证明"不是代码把超时设错了"）

| 探针 | 结果 | 结论 |
|---|---|---|
| `GET agnes /v1/models` | HTTP 200，**2.43s** | Key 有效、网络通、`agnes-3.0-flash` 在列 |
| `GET ly77625 /v1/models` | HTTP 200，**2.61s** | Key 有效、`gemini-3.8-flash` 在列 |
| `POST agnes chat`（32 token，curl） | HTTP 200，**2.75s** | 最小请求是快的 |
| `POST agnes chat`（与 router 同 payload，`requests`） | 第 1 次 HTTP 200 **2.80s**；**紧接着同一条请求 → read timeout 30s** | 🔴 **上游时延极不稳定 / 突发后疑似被限流排队** |
| `POST ly77625 chat`（32 token） | HTTP 200，**5.59s** | 正常 |

**判定**：超时**不是** `timeout_cap` 配错，也不是链路坏了 —— 三条独立证据链：

1. **直连对照组**：同一个上游 `GET /v1/models` 只要 2.4s，但**同一条 chat 请求连打两次，第 2 次直接挂住 >30s** → 上游长尾/突发限流。
2. **run D（小 prompt）在同一套代码、同一 tier、同一 provider 上成功**：163 字符 prompt → **5.5s / 58 字 / JSON 严格可解析**。说明 `agnes` 不是不可用，是"**输入越大、期望输出越长，越吃不确定的长尾**"。
3. **设计期基线**（`src/core/llm_task_tier.py` 注释原文）：`:63` 记 **「deep 实测 9.7~16.5s」**、`:60` 记 **「agnes（E1 实测）：JSON 严格、582 tokens 完整 7 分析师 schema」** → 25s cap 是按**当时实测**留了余量的，本次是**当前**上游劣于基线，**不是 cap 定错**。

**量化对比（同一套代码，只改 prompt 规模）**：

| 样本 | 输入 | 期望输出 | 结果 |
|---|---|---|---|
| run D（本报告授权的小 prompt） | **163 字符** | 3 字段 / 58 字 | ✅ **5.5s 成功**，首选命中 |
| run 1/2/3（业务 `analyze_fund_with_agents`） | **3175 字符**（≈2000 tokens）+ 真实数据更大 | 7 分析师完整 schema（设计基线 582 tokens） | ❌ 25s + 20s 双跳全超时 |

→ **结论：`cap` 与预算都不要改。** 唯一需要线上确认的是 GLM 首跳（见 §5 F2），因为 GLM 的 20s cap 是否宽裕，本地无法验证（无 `ZHIPU_API_KEY`）。

### 2.4 数据源失败 vs LLM 失败（已严格区分）

**先澄清一个容易误判的点：本地主数据源是好的。** 独立复核（零 LLM 成本，`from src.core import data_source_v2 as ds2`）：

| 探针 | 实测 |
|---|---|
| `ds2.get_fund_history_tencent('002891','1y')` | **241 行 / 0.31s**，首行 `{"date":"2025-11-07","nav":1.635,"change_pct":-0.24}` |
| `ds2.get_fund_realtime_tencent(['002891'])` | 1 条 / 0.3s，`nav=1.895, change_pct=-10.15`，名称「华夏移动互联混合(QDII)」 |

本地失败的只是 **4 个次级源**（均依赖 EastMoney push2 / akshare）：板块轮动、市场情绪、北向资金、持仓（em/ak）、新闻（人气榜 / 重仓股新闻）。它们被 sandbox 代理拦截（`EastMoney push2 API unavailable (proxy blocked)`）。
